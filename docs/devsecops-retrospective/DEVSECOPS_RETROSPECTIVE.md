## 3. Implemented Controls

### US068 — Evidence of Successful Pipeline Stages

Four GitHub Actions workflows provide objective, auditable, and tamper-evident delivery evidence:

- **Hardened Security Pipeline** (`hardened-security-pipeline.yml`): jobs `gitleaks`, `semgrep-sast`, `config-scan`, `license-scan`, and `build-and-test-with-coverage` — each producing downloadable artifacts and/or automated PR comments with timestamped results.
- **Build, Scan and Publish Docker Images** (`docker-image.yml`): jobs `backend` and `frontend` — building, scanning with Trivy, and publishing versioned images with OCI labels.
- **Notify Discord on PR Creation** and **Notify Discord on PR Merge**: job `notify` — providing team-wide visibility of pipeline events via Discord.

Evidence is not a manual video demonstration but the artifacts and comments automatically generated by the pipeline itself: objective, timestamped, and directly linked to workflow runs. Key learning: the most professional and auditable form of delivery evidence is produced natively by the pipeline — not recorded separately. Timestamped PR comments and downloadable artifacts provide a tamper-evident audit trail that a video cannot match.

### US069 — Security Code Review Checklist in Pull Requests

A security checklist was added to the `pull_request_template`, covering input validation, access control, secrets/configuration, logging, error handling, dependencies, and CI security gates. The checklist explicitly marks authentication/authorization/ACL as N/A for this sprint (not yet implemented), while preserving checks on existing link visibility rules. The main learning was the importance of making each item specific and verifiable — tied to features that actually exist — rather than producing a generic checklist impossible to fulfil.

### US070 — Dependency Lock Files

`package-lock.json` is committed to the repository and used via `npm ci` in CI to guarantee deterministic frontend builds. Backend dependencies are managed through Maven (`pom.xml`), which already provided reproducible builds. The CI pipeline was updated to run `npm ci`, followed by tests and coverage, ensuring that dependency integrity is validated automatically on every push. Key learning: a deterministic install is not sufficient by itself — tests must follow immediately to confirm the system is not broken after dependency resolution.

### US071 — Dependency Scanning for CVEs and License Risks

OWASP Dependency-Check is integrated into the Maven `verify` phase and generates detailed CVE reports based on NVD data. License risk analysis was added via the License Maven Plugin, which generates a license inventory, validates compliance against a defined policy (approved/restricted/non-approved), and posts findings to pull requests via a dedicated `license-scan` CI job. The license scan was separated from the main build job to improve visibility. Key learning: dependency security is not limited to CVEs — legally non-compliant licenses are an equally real risk that requires explicit policy enforcement.

### US072 — Secure Dockerfiles

Both backend and frontend Dockerfiles use multi-stage builds, SHA256-pinned base images, and `.dockerignore` files to minimise build context. Initial Dockerfiles used standard tags; they were updated to pinned digests for improved reproducibility and supply-chain security. Key learning: pinning images by digest eliminates the risk of silent tag mutation but requires active tracking of image updates.

### US073 — Automatic Docker Image Scanning

Trivy is integrated into the `Build, Scan and Publish Docker Images` GitHub Actions workflow. Both frontend and backend Dockerfiles were updated during this sprint to address HIGH and CRITICAL vulnerabilities identified by Trivy. The process was straightforward — the main effort was in iterating on base image selection until a version with no HIGH/CRITICAL findings was found.

### US074 — Hardened Container Runtime Settings

Both services run as non-root users (`appuser` for the backend, `nginx` for the frontend). The frontend uses `nginxinc/nginx-unprivileged` (pinned by SHA256 digest) to run fully non-root on port 8080. `docker-compose.yml` enforces `no-new-privileges: true`, `cap_drop: [ALL]`, and CPU/memory resource limits. Key learnings: the SAST rule failed when the frontend Dockerfile did not explicitly declare `USER nginx`, even though the unprivileged image defaults to non-root — an explicit declaration is required. Proper runtime hardening requires restrictive runtime flags and resource limits in addition to non-root user configuration.

### US075 — Secure Docker Compose Configuration

`docker-compose.yml` orchestrates backend and frontend with only necessary ports exposed (8081 backend, 8080 frontend), a single named volume for H2 persistence, and explicit environment variables without secrets. Health checks are defined for both services; frontend startup is conditioned on `service_healthy` for the backend via `depends_on`. Runtime hardening flags from US074 are applied at this layer. Key learnings: the H2 volume ownership was incompatible with the non-root user introduced in US074 (error 90097) and required correction; the frontend health check used `localhost` which resolved to IPv6 (`::1`) inside the container while nginx bound only to IPv4 — fixed by using `127.0.0.1`; CORS was configured for the Vite dev port (5173) rather than the container port (8080), blocking API calls from the containerised frontend.

### US076 — Docker Image Versioning and Traceability

Images are built and published via `.github/workflows/docker-image.yml` using `docker/metadata-action` and `docker/build-push-action`, with OCI labels (version, commit SHA, build date) embedded in each image. A `delivery-evidence` job collects and publishes this metadata as a CI artifact. Key learning: the project already had partial versioning via SHA tags but lacked auditability; separating `pull_request` (validate only) from `push` (build and publish) events was important to ensure the evidence accurately reflects whether an image was merely validated or actually published.

### US077 — OWASP Security Tests

A dedicated test suite tagged `@Tag("security")` was added covering OWASP Top 10 risks relevant to the application: A01 (Broken Access Control), A03 (Injection), A04 (Insecure Design), A05 (Security Misconfiguration), A07 (Identification and Authentication), A08 (Software and Data Integrity), A09 (Logging and Monitoring), A10 (SSRF). Tests use `@WebMvcTest + MockMvc` for HTTP behaviour and plain JUnit with `Properties.load()` for configuration file validation. The suite runs within the existing `mvn test` job and can be isolated with `-Dtest="*SecurityTest"`. Key learnings: `when(mock.voidMethod()).thenThrow()` is a compilation error with Mockito — `doThrow(...).when(mock).voidMethod()` is the correct pattern; not all endpoints propagate exceptions to `CustomRestExceptionHandler` — some controllers have internal catch blocks; the accepted-risk pattern inverts normal test logic: a test passes because a known problem exists, and will fail if the vulnerability is fixed (which is the intended behaviour).

### US078 — Documentation of Unresolved Security Findings

Unresolved security findings are documented with explicit mitigation decisions and accepted risk statements, ensuring visibility before final delivery. Each finding is classified as either resolved, accepted with justification, or deferred to a future sprint.

## 7. Key Lessons Learned

1. **Pipeline artifacts are better evidence than videos** — automatically generated artifacts and timestamped PR comments are objective, tamper-evident, and directly auditable in a way that a video demonstration cannot match.
2. **Deterministic builds require more than `npm ci`** — tests must follow immediately to confirm the system is not broken after dependency resolution.
3. **Dependency security is not limited to CVEs** — license compliance is an equally real risk requiring explicit policy definition and automated enforcement.
4. **Non-root containers require explicit USER declarations** — even when the base image defaults to non-root, SAST tools require an explicit `USER` instruction in the Dockerfile.
5. **Runtime hardening is a multi-layer concern** — non-root user, `no-new-privileges`, capability dropping, and resource limits are all necessary; none alone is sufficient.
6. **Integration exposes coupling between US** — each US was implemented correctly in isolation, but integration revealed incompatibilities (H2 volume ownership, IPv4/IPv6 health check resolution, CORS port mismatch) that only surfaced when all controls were combined.
7. **The accepted-risk test pattern is intentionally inverted** — a passing test documents a known limitation; fixing the vulnerability makes the test fail, which is the correct behaviour for tracking accepted risks.
8. **Pipeline scope matters** — separating `pull_request` from `push` events, and separating license scanning from the main build job, significantly improved visibility and auditability of each individual control.
